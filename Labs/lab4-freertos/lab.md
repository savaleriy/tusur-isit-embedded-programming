## 2. Цель работы

Спроектировать и реализовать многозадачную систему на FreeRTOS, обосновать распределение приоритетов и ресурсов, измерить её временные характеристики и сравнить с реализацией на кооперативной многозадачности.

## 3. Способ реализации

Допустимы пути **B (объектный C++)** и **C (смешанный)**.

Обратите внимание на особенность: FreeRTOS написана на C, и `xTaskCreate()` принимает **свободную функцию**, а не метод класса. Обёртывание задач в классы - самостоятельное проектное решение, которое нужно принять и обосновать. Типовой приём - статический метод-переходник, получающий `this` через параметр задачи:

```cpp
class SensorTask {
public:
    void start() {
        xTaskCreate(&SensorTask::trampoline, "sens", 128, this, 2, nullptr);
    }
private:
    static void trampoline(void* arg) {
        static_cast<SensorTask*>(arg)->run();
    }
    void run();   // здесь бесконечный цикл задачи
};
```

Если вы выбрали путь B, такой переходник (или эквивалентное решение) обязателен, а его устройство объясняется в отчёте. Путь C - задачи свободными функциями, драйверы классами - тоже полностью допустим.

## 4. Оборудование

**Обязательный минимум:**

- Arduino UNO;
- дисплей (1602 через I2C или TFT ILI9341);
- **не менее двух датчиков разного характера**: один быстрый аналоговый (фоторезистор, LM35, потенциометр) и один медленный блокирующий (DHT-11 или HC-SR04);
- устройство ввода, **обязательно подключённое к прерыванию** (D2 или D3): кнопка, джойстик или энкодер KY-040;
- исполнительное устройство: сервопривод, реле или светодиодная матрица;
- зуммер.

Остальное определяется вариантом.

## 5. Базовое задание

### 5.1. Состав задач

Система содержит **не менее четырёх задач FreeRTOS**, каждая со своим обоснованным приоритетом.

Ориентировочный состав (конкретный вы определяете сами и обосновываете в отчёте):

| Задача | Приоритет | Назначение |
| --- | --- | --- |
| Обработчик событий | Высокий (3) | Отложенная обработка прерывания от кнопки или датчика |
| Опрос датчиков | Средний (2) | Периодическое чтение, включая блокирующий датчик |
| Управление | Средний (2) | Логика: пороги, исполнительные устройства |
| Отображение | Низкий (1) | Обновление дисплея |
| Монитор | Низкий (1) | Диагностика системы |

### 5.2. Обязательные механизмы

Система использует **все** перечисленные механизмы, каждый - по назначению:

1. **Очередь** для передачи данных между задачами.
2. **Мьютекс** для защиты разделяемого ресурса **или** выделенная задача-владелец ресурса. Выбор обоснуйте.
3. **Семафор или уведомление задачи** для связи прерывания с задачей.
4. **Аппаратное прерывание** с отложенной обработкой и корректной работой с `xHigherPriorityTaskWoken`.
5. **Задача-монитор**, периодически выводящая диагностику: свободная куча, остатки стеков всех задач, заполненность очередей, счётчики потерь.

### 5.3. Требования к реализации

Помимо [общих требований](../README.md#4-общие-технические-требования):

1. Результат создания **каждой** задачи, очереди и семафора проверяется; при ошибке выводится диагностика.
2. Включена проверка переполнения стека (`configCHECK_FOR_STACK_OVERFLOW`) с реализованным обработчиком.
3. Размеры стеков подобраны экспериментально по `uxTaskGetStackHighWaterMark()` с запасом 30-50 байт.
4. Обработчики прерываний используют **только** функции с суффиксом `FromISR`.
5. Динамическое выделение памяти вне внутреннего механизма FreeRTOS не применяется.

### 5.4. Обязательные измерения

Основная часть работы. Без неё работа не принимается.

**Ресурсы:**

| Показатель | Как получить |
| --- | --- |
| Flash и статическая SRAM | Отчёт компилятора |
| Свободная куча FreeRTOS после запуска | `xPortGetFreeHeapSize()` |
| Остаток стека каждой задачи | `uxTaskGetStackHighWaterMark()` |
| Итоговый бюджет памяти | Таблица со всеми составляющими |

Составьте таблицу бюджета памяти по образцу из [занятия 21](../../Practice/21-freertos-isr/note.md) и сопоставьте расчёт с фактом.

**Временные характеристики:**

| Показатель | Требование |
| --- | --- |
| Время выполнения обработчика прерывания | В микросекундах |
| Время от события до начала задачи-обработчика | Среднее и **максимальное** по не менее чем 20 измерениям |
| Джиттер периодической задачи | Минимум, максимум, разброс |
| Влияние `taskYIELD()` в ISR | Измерения с ним и без него |

Опишите способ измерения каждой величины.

**Поведение при перегрузке:**

1. Искусственно замедлите задачу-получатель так, чтобы очередь начала переполняться. Приведите статистику потерь.
2. Определите максимальную частоту событий, которую система обрабатывает без потерь.
3. Опишите, как система деградирует: что теряется первым и остаётся ли она работоспособной.

### 5.5. Сравнение с кооперативной моделью

Обязательная часть работы.

1. Реализуйте **ту же** функциональность на кооперативной многозадачности с `millis()` и конечными автоматами ([занятие 7](../../Practice/07-timing-multitasking/note.md)). Допустимо взять за основу свою ЛР 3, если функциональность сопоставима, - укажите это в отчёте.
2. Сравните обе версии:

| Критерий | FreeRTOS | Кооперативная |
| --- | --- | --- |
| Flash, байт | | |
| SRAM статическая, байт | | |
| Свободная SRAM во время работы, байт | | |
| Худшее время реакции на кнопку, мс | | |
| Джиттер периодической задачи, мс | | |
| Количество строк кода | | |
| Время разработки, часов | | |

3. Добавьте в **обе** версии одну новую функцию (например, журналирование в EEPROM) и оцените, где это далось проще и почему.
4. Сформулируйте **аргументированный вывод**: какой подход вы выбрали бы для этой задачи и при каких условиях изменили бы решение.

> Вывод "FreeRTOS лучше, потому что современнее" не засчитывается. Нужны цифры и аргументы.

## 6. Варианты

Вариант выбирается студентом самостоятельно. Каждый задаёт **прикладную задачу** и **обязательный механизм ОСРВ**, который в ней требуется освоить сверх базового набора.

### Вариант 1. "Метеостанция"

**Задача:** сбор данных с трёх датчиков разной скорости, отображение, журнал, тревоги по порогам.

**Механизм:** **программные таймеры** FreeRTOS (`xTimerCreate`) вместо отдельных задач для периодических действий. В отчёте - сравнение расхода памяти с вариантом на задачах.

### Вариант 2. "Охранная система"

**Задача:** контроль датчиков открытия, вибрации и движения; постановка на охрану, задержка на выход, сирена, журнал.

**Механизм:** **группы событий** (`EventGroup`) для ожидания комбинации срабатываний нескольких датчиков одной задачей.

### Вариант 3. "Инкубатор"

**Задача:** поддержание температуры и влажности регулятором с гистерезисом, поворот лотка сервоприводом по расписанию, аварийная сигнализация.

**Механизм:** **приоритетная инверсия** - воспроизведите её на двоичном семафоре, покажите на измерениях, затем устраните мьютексом с наследованием приоритета и покажите разницу в цифрах.

### Вариант 4. "Аквариум"

**Задача:** контроль температуры и уровня воды, освещение по расписанию, кормление сервоприводом, тревоги.

**Механизм:** **очередь команд** с приоритетами: аварийные команды обгоняют обычные. Реализуйте через две очереди и обоснуйте выбор.

### Вариант 5. "Перекрёсток"

**Задача:** два светофора с пешеходными кнопками, ночной режим мигания, аварийный режим.

**Механизм:** **уведомления задач** (`xTaskNotify`) вместо семафоров. Измерьте выигрыш по памяти и скорости относительно семафоров и приведите обе реализации.

### Вариант 6. "Парковка"

**Задача:** учёт занятых мест по датчикам, шлагбаум на сервоприводе, табло свободных мест, доступ по RFID.

**Механизм:** **взаимная блокировка** - воспроизведите её намеренно (две задачи, два мьютекса), покажите, как она проявляется, и реализуйте два разных способа устранения.

### Вариант 7. "Станок с ЧПУ"

**Задача:** управление шаговым двигателем по программе перемещений, концевые датчики, аварийный останов, индикация.

**Механизм:** **жёсткий деталайн**. Задача шагового двигателя должна выдерживать период с джиттером не более 1 мс. Докажите измерениями, что деталайн соблюдается, и покажите, при какой нагрузке он нарушается.

### Вариант 8. "Робот-тележка"

**Задача:** движение по линии (KY-033), объезд препятствий (HC-SR04), контроль скорости (SR-393), телеметрия в Serial.

**Механизм:** **разделение по частотам**. Три контура с разными периодами (управление, датчики, телеметрия). Обоснуйте выбор периодов и покажите, что медленный контур не мешает быстрому.

### Вариант 9. "Регистратор на SD-карте"

**Задача:** непрерывный сбор данных с записью на карту, дисплей, меню, тревоги.

**Механизм:** **работа с блокирующим ресурсом**. Запись на карту занимает от единиц до сотен миллисекунд с большим разбросом. Вынесите её так, чтобы это не влияло на отзывчивость интерфейса; измерьте время реакции интерфейса во время записи и докажите, что оно не выросло.

### Вариант 10. "Энергоэффективная система"

**Задача:** автономный регистратор, просыпающийся по расписанию.

**Механизм:** **`vApplicationIdleHook()`** с переводом ядра в сон в холостой задаче. Измерьте потребление до и после, объясните, почему при работающем планировщике нельзя использовать `PWR_DOWN`, и какой режим применим.

### Вариант 11. "Музыкальный автомат"

**Задача:** воспроизведение мелодий на пассивном зуммере, выбор через меню, световое сопровождение на матрице, управление с ИК-пульта.

**Механизм:** **конкуренция за таймеры**. `tone()` занимает Timer2, развёртка матрицы - ещё один таймер, FreeRTOS - третий. Разрешите конфликт, опишите распределение таймеров и покажите, что происходит при неправильном.

### Вариант 12. "Распределённая система"

**Задача:** две платы: сбор данных и пульт управления, обмен по UART.

**Механизм:** **задачи приёма и передачи** на каждой стороне с очередями на обоих направлениях. Измерьте время доставки команды, процент потерь при помехах и покажите, как система восстанавливается после обрыва связи.

## 9. Порядок выполнения

**Начните с проектирования, а не с кода.** Задача 21.8 - это первый раздел вашего отчёта. Система, спроектированная на бумаге, отлаживается втрое быстрее.

**Считайте память заранее.** На UNO это не формальность: программа может просто не запуститься, и без проверки результата `xTaskCreate()` вы будете искать ошибку в логике.

**Добавляйте задачи по одной.** Запустите две, убедитесь, что работают, добавьте третью. Ошибки синхронизации проще ловить, когда известно, что именно вы только что изменили.

**Заведите задачу-монитор с самого начала.** Она окупится многократно.

**Не отлаживайте печатью изнутри критических секций.** Вывод в Serial меняет тайминги настолько, что ошибка исчезает - и возвращается, как только отладку убирают.

**Помните про 15-миллисекундный тик.** Если что-то требует более точного времени - это работа для аппаратного таймера, а не для задачи.
