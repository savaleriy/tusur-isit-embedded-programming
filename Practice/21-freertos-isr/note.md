# Занятие 21. FreeRTOS: прерывания, тайминги и ресурсы

**Цель занятия:** научиться правильно связывать прерывания с задачами, оценивать реальные временные характеристики системы и принимать обоснованное решение о том, нужна ли ОСРВ в конкретном проекте.

**Что понадобится:** Arduino UNO, PlatformIO, кнопки, датчики, светодиоды, логический анализатор или второй Arduino (по возможности).

---

## 1. Прерывания и планировщик

Прерывание и задача - разные миры. Прерывание обслуживается аппаратурой микроконтроллера и **не подчиняется планировщику**: обработчик выполняется немедленно, вытесняя любую задачу, включая самую приоритетную.

Из этого следует главное ограничение: **обработчик прерывания не может блокироваться**. Он не может ждать мьютекс, ждать данные из очереди или вызвать `vTaskDelay()` - блокировать нечего, обработчик не является задачей и у него нет собственного контекста для сохранения.

Поэтому у функций FreeRTOS существуют **отдельные версии для вызова из прерываний** - с суффиксом `FromISR`:

| Обычная функция | Версия для ISR |
| --- | --- |
| `xQueueSend()` | `xQueueSendFromISR()` |
| `xQueueReceive()` | `xQueueReceiveFromISR()` |
| `xSemaphoreGive()` | `xSemaphoreGiveFromISR()` |
| `xSemaphoreTake()` | `xSemaphoreTakeFromISR()` |
| `xTaskNotifyGive()` | `vTaskNotifyGiveFromISR()` |

Версии `FromISR` никогда не блокируются: они либо выполняют операцию сразу, либо возвращают ошибку.

**Вызов обычной версии из обработчика прерывания приводит к неопределённому поведению.** Это одна из самых частых и самых трудноуловимых ошибок в программах на FreeRTOS.

### Параметр `xHigherPriorityTaskWoken`

Все функции `FromISR` принимают дополнительный параметр:

```cpp
void onButtonISR() {
    BaseType_t xHigherPriorityTaskWoken = pdFALSE;

    xSemaphoreGiveFromISR(xButtonSemaphore, &xHigherPriorityTaskWoken);

    if (xHigherPriorityTaskWoken == pdTRUE) {
        taskYIELD();          // немедленно переключиться на разблокированную задачу
    }
}
```

> Смысл: операция в обработчике могла **разблокировать задачу**, приоритет которой выше, чем у прерванной. Функция сообщает об этом, выставляя флаг.

Без вызова `taskYIELD()` система вернётся в прерванную задачу и переключится на более приоритетную только на следующем системном тике - то есть **через 15 мс на UNO**. Для быстрой реакции это неприемлемо.

Практическое следствие: сам по себе семафор из прерывания не гарантирует быстрой реакции. Гарантирует его связка с немедленным переключением.

## 2. Отложенная обработка прерывания

Канонический приём FreeRTOS: обработчик делает минимум, вся работа выполняется в задаче.

```cpp
SemaphoreHandle_t xEventSemaphore;

void onSensorISR() {
    BaseType_t woken = pdFALSE;
    xSemaphoreGiveFromISR(xEventSemaphore, &woken);
    if (woken) taskYIELD();
}

void TaskSensorHandler(void *pv) {
    for (;;) {
        if (xSemaphoreTake(xEventSemaphore, portMAX_DELAY) == pdTRUE) {
            // здесь доступно всё: Serial, I2C, задержки, вычисления
            readSensorOverI2C();
            processData();
            Serial.println(F("Событие обработано"));
        }
    }
}
```

Задачу-обработчик принято называть **отложенным обработчиком прерывания** (`deferred interrupt handler`). Ей назначают высокий приоритет, чтобы она начала выполняться сразу после выхода из ISR.

Что это даёт по сравнению с обработкой внутри ISR:

| | Внутри ISR | В задаче |
| --- | --- | --- |
| Длительность | Должна быть минимальной | Любая |
| Доступ к Serial, I2C | Нельзя | Можно |
| `vTaskDelay()` | Нельзя | Можно |
| Мьютексы, очереди | Только `FromISR` | Полный набор |
| Блокирует другие прерывания | Да | Нет |

### Передача данных из прерывания

Если событие несёт данные, вместо семафора используют очередь:

```cpp
QueueHandle_t xTimestampQueue;

void onPulseISR() {
    BaseType_t woken = pdFALSE;
    unsigned long timestamp = micros();          // micros() из ISR читать можно

    xQueueSendFromISR(xTimestampQueue, &timestamp, &woken);
    if (woken) taskYIELD();
}

void TaskPulseProcessor(void *pv) {
    unsigned long ts, prev = 0;
    for (;;) {
        if (xQueueReceive(xTimestampQueue, &ts, portMAX_DELAY) == pdTRUE) {
            unsigned long period = ts - prev;
            prev = ts;
            Serial.println(1000000UL / period);   // частота в герцах
        }
    }
}
```

Очередь берёт на себя буферизацию: если импульсы приходят пачкой, задача обработает их по очереди, ничего не потеряв (до заполнения очереди).

### Уведомления задач

Более экономный механизм, чем семафор: у каждой задачи есть встроенное уведомление, для которого не нужен отдельный объект.

```cpp
TaskHandle_t xHandlerTask;

void onISR() {
    BaseType_t woken = pdFALSE;
    vTaskNotifyGiveFromISR(xHandlerTask, &woken);
    if (woken) taskYIELD();
}

void TaskHandler(void *pv) {
    for (;;) {
        ulTaskNotifyTake(pdTRUE, portMAX_DELAY);     // ждём уведомления
        handleEvent();
    }
}
```

Уведомления работают быстрее семафоров и **не занимают дополнительной памяти** - что на UNO с 2 КБ ОЗУ весомый аргумент. Ограничение: уведомление адресуется **конкретной задаче**, тогда как семафор может ждать любая.

## 3. Что можно и что нельзя в обработчике

**Можно:**

- читать и писать регистры и выводы (`digitalWrite`, прямая работа с портами);
- читать `micros()` и `millis()` (но они не будут увеличиваться внутри обработчика);
- изменять переменные, объявленные `volatile`;
- вызывать функции с суффиксом `FromISR`;
- `delayMicroseconds()` - она основана на подсчёте тактов.

**Нельзя:**

- вызывать обычные функции FreeRTOS без `FromISR`;
- вызывать `vTaskDelay()`, `delay()`;
- работать с `Serial`, I2C, SPI - они сами основаны на прерываниях;
- захватывать мьютексы;
- выполнять длительные вычисления.

**Критические секции в ISR** имеют собственную форму:

```cpp
UBaseType_t saved = taskENTER_CRITICAL_FROM_ISR();
// короткий участок
taskEXIT_CRITICAL_FROM_ISR(saved);
```

## 4. Временные характеристики системы

Чтобы утверждать, что система работает "в реальном времени", нужно уметь измерять её характеристики.

### Основные величины

| Величина | Что означает |
| --- | --- |
| **Латентность прерывания** | От аппаратного события до первой инструкции ISR |
| **Время выполнения ISR** | Длительность обработчика |
| **Латентность планировщика** | От разблокировки задачи до её выполнения |
| **Время реакции** | Полное время от события до реакции системы |
| **Джиттер** | Разброс времени реакции между срабатываниями |

Для системы реального времени важна не средняя величина, а **худший случай**. Система, реагирующая за 1 мс в среднем и за 40 мс в худшем случае, для управления не годится.

### Ориентировочные цифры для UNO с FreeRTOS

| Операция | Порядок величины |
| --- | --- |
| Вход в обработчик прерывания | 2-4 мкс |
| Переключение контекста задач | 10-20 мкс |
| `xQueueSend` / `xQueueReceive` | 20-40 мкс |
| Захват свободного мьютекса | 15-25 мкс |
| Системный тик (WDT) | **15 мс** |
| Задержка реакции без `taskYIELD()` в ISR | до 15 мс |

Главный вывод из таблицы: **системный тик в 15 мс определяет всё**. Любая задача, пробуждённая по времени, имеет джиттер до 15 мс. Именно поэтому FreeRTOS на UNO не подходит для задач с требованиями лучше десятков миллисекунд - там нужны прерывания и аппаратные таймеры.

### Как измерить

**Осциллографом или логическим анализатором.** Самый точный способ: поднять вывод в момент события, опустить в момент реакции, измерить длительность импульса.

```cpp
void onISR() {
    PORTB |= (1 << PB0);                     // метка: событие произошло
    BaseType_t woken = pdFALSE;
    xSemaphoreGiveFromISR(xSem, &woken);
    if (woken) taskYIELD();
}

void TaskHandler(void *pv) {
    for (;;) {
        xSemaphoreTake(xSem, portMAX_DELAY);
        PORTB &= ~(1 << PB0);                // метка: задача начала работу
        // ...
    }
}
```

**Программно через micros().** Менее точно (само измерение занимает время), но доступно всегда:

```cpp
volatile unsigned long eventTime;
unsigned long worstLatency = 0;

void onISR() {
    eventTime = micros();
    BaseType_t woken = pdFALSE;
    xSemaphoreGiveFromISR(xSem, &woken);
    if (woken) taskYIELD();
}

void TaskHandler(void *pv) {
    for (;;) {
        xSemaphoreTake(xSem, portMAX_DELAY);
        unsigned long latency = micros() - eventTime;
        if (latency > worstLatency) worstLatency = latency;
    }
}
```

Обязательно фиксируйте **максимум**, а не среднее.

## 5. Бюджет ресурсов

Полный учёт памяти для типичной программы на UNO:

```
Всего SRAM                                      2048 байт
  - ядро FreeRTOS и служебные структуры         ~200 байт
  - глобальные переменные программы             ~150 байт
  - буферы библиотек (Serial: 64 + 64)          ~130 байт
  - стек задачи Idle                            ~85 байт
  - стек задачи 1 (датчик)                       192 байта
  - стек задачи 2 (дисплей)                      256 байт
  - стек задачи 3 (управление)                   128 байт
  - очередь 5 x 8 байт + служебные                70 байт
  - мьютекс                                       ~20 байт
  ----------------------------------------------------
  Итого                                        ~1231 байт
  Свободно                                      ~817 байт
```

Запас в 800 байт кажется большим, но он расходуется быстро: локальный буфер `char buf[64]` в задаче, добавление ещё одной задачи, увеличение очереди.

### Практические правила

1. **Подбирайте стеки экспериментально** через `uxTaskGetStackHighWaterMark()`, а не наугад. Ставьте запас 30-50 байт.
2. **Считайте буферы библиотек.** Serial занимает 128 байт под приём и передачу. При нехватке памяти их размер можно уменьшить в `HardwareSerial.h`.
3. **Очереди - самый дорогой механизм.** Уведомления задач бесплатны, семафоры дешевле очередей.
4. **Проверяйте результат создания** каждой задачи, очереди и семафора.
5. **Не создавайте объекты во время работы.** Всё создавайте в `setup()` - так нехватка памяти обнаружится сразу, а не через час.

## 6. Комбинирование ОСРВ и прерываний

FreeRTOS не отменяет прерывания и аппаратные таймеры - она с ними сочетается. Правильное разделение выглядит так:

| Требование ко времени | Механизм |
| --- | --- |
| Микросекунды, точный отсчёт | Аппаратный таймер, прерывание |
| Единицы миллисекунд | Прерывание плюс отложенная обработка |
| Десятки миллисекунд | Задача с `vTaskDelay()` |
| Когда есть свободное время | Задача с низким приоритетом |

Пример распределения в реальном проекте:

```
Аппаратный Timer1 (прерывание)  -> развёртка светодиодной матрицы, 1 кГц
Прерывание INT0                 -> фиксация импульсов энкодера
Задача приоритета 3             -> отложенная обработка событий энкодера
Задача приоритета 2             -> опрос датчиков раз в 500 мс
Задача приоритета 1             -> обновление дисплея
Задача Idle                     -> сон процессора
```

Развёртка матрицы **не должна** быть задачей: 15-миллисекундный тик даст видимое мерцание. Это работа для аппаратного таймера.

## 7. Итог: нужна ли ОСРВ

Честный ответ для Arduino UNO - **чаще нет, чем да**.

### Аргументы против на этой платформе

- ядро съедает 200 байт из 2048 и 6-10 КБ Flash;
- каждая задача требует минимум 100 байт стека;
- системный тик 15 мс делает точное управление невозможным;
- переполнение стека даёт сбои, которые трудно найти;
- отладка многозадачных программ существенно сложнее.

### Аргументы за

- линейный код вместо конечных автоматов - крупный выигрыш в читаемости;
- приоритеты дают гарантию времени реакции для критичных задач;
- очереди и мьютексы решают задачи, которые в кооперативной модели решаются вручную и с ошибками;
- архитектура масштабируется: программа не разваливается при добавлении пятой задачи;
- **это стандарт отрасли** - навык переносится на STM32, ESP32, промышленные контроллеры.

### Как выбирать

Задайте себе три вопроса:

1. **Есть ли задачи с разными требованиями ко времени реакции?** Если все задачи одинаково нетребовательны - ОСРВ не нужна.
2. **Есть ли длительные блокирующие операции, которые нельзя переписать?** Если всё быстрое - кооперативная модель проще.
3. **Хватит ли памяти?** Посчитайте бюджет **до** начала работы, а не после.

Если хотя бы на два вопроса ответ отрицательный - используйте кооперативную многозадачность с [занятия 7](../07-timing-multitasking/note.md). Она проще, предсказуемее и на UNO чаще уместнее.

### Что дальше

Знания этого блока полностью переносятся на другие платформы, где ОСРВ действительно уместна:

- **STM32** (64-512 КБ ОЗУ) - FreeRTOS входит в состав STM32CubeMX, применяется повсеместно;
- **ESP32** (520 КБ ОЗУ, два ядра) - FreeRTOS является частью ESP-IDF и работает всегда, даже в скетчах Arduino;
- **Zephyr, RT-Thread, ChibiOS** - альтернативные ОСРВ с похожими концепциями.

Задачи, приоритеты, очереди, семафоры, приоритетная инверсия, отложенная обработка прерываний - это словарь, общий для всех этих систем.
