# Занятие 7. Время и кооперативная многозадачность

**Цель занятия:** избавиться от `delay()` и научиться писать программы, которые одновременно делают несколько дел: мигают, опрашивают кнопки, читают датчики и выводят данные - не мешая друг другу.

**Что понадобится:** Arduino UNO, светодиоды, кнопки, любой датчик с предыдущих занятий.

---

## 1. Функции работы со временем

### `delay(ms)`

Приостанавливает выполнение программы на заданное число миллисекунд. Реализована как пустой цикл, который крутится, отслеживая `millis()`.

Главный недостаток: **процессор полностью занят**. В течение задержки не выполняется ничего - не читаются кнопки, не опрашиваются датчики, не обрабатывается ввод из Serial.

### `delayMicroseconds(us)`

То же самое, но в микросекундах. Важное отличие в реализации: она построена не на таймере, а на **подсчёте тактов процессора**, поэтому работает и при запрещённых прерываниях - в том числе **внутри обработчика прерывания**. Это делает её пригодной для формирования точных коротких импульсов (например, для датчика HC-SR04 или программной реализации протокола).

Ограничение: точность гарантирована для значений примерно до 16 000 мкс.

### `millis()` и `micros()`

Возвращают время, прошедшее с момента запуска программы. Не останавливают выполнение - просто сообщают текущее показание счётчика.

| Функция | Тип | Разрешение | Переполнение |
| --- | --- | --- | --- |
| `millis()` | `unsigned long` | 1 мс | через ~49,7 суток |
| `micros()` | `unsigned long` | 4 мкс (не 1!) | через ~71,6 минуты |

Разрешение `micros()` составляет 4 микросекунды, потому что Timer0 на UNO тактируется с предделителем 64: одно приращение счётчика - это 4 мкс.

Обе функции работают на **Timer0**, который заодно обслуживает ШИМ на выводах D5 и D6. Отсюда важное следствие: **перенастройка Timer0 ломает все функции времени сразу**.

## 2. Неблокирующая задержка

Базовая конструкция всего курса:

```cpp
unsigned long lastRun = 0;
const unsigned long INTERVAL = 500;

void loop() {
    if (millis() - lastRun >= INTERVAL) {
        lastRun = millis();
        // действие, выполняемое раз в 500 мс
    }
    // сюда управление приходит тысячи раз в секунду - здесь можно делать что-то ещё
}
```

Смысл: вместо "остановись на 500 мс" программа спрашивает "прошло ли 500 мс с прошлого раза?" и в остальное время занимается другими делами.

### Почему именно `millis() - lastRun >= INTERVAL`

Начинающие часто пишут иначе:

```cpp
if (millis() >= lastRun + INTERVAL)   // НЕПРАВИЛЬНО
```

Разница проявляется через 49,7 суток непрерывной работы, когда `millis()` переполняется и начинает счёт с нуля. В первом варианте вычитание беззнаковых чисел даёт **правильную разницу даже при переполнении** - благодаря свойствам арифметики по модулю $2^{3^{2}}$. Во втором варианте сложение переполнится, условие никогда не выполнится, и программа зависнет навсегда.

Проверить это можно, не дожидаясь 50 суток: подставьте `unsigned long now = 4294967290UL` и `lastRun = 4294967200UL` и посчитайте оба выражения вручную.

По той же причине переменные времени **обязаны** быть типа `unsigned long`. Тип `int` переполнится через 32 секунды, `long` даст отрицательные значения.

### Дрейф и его устранение

Есть два способа сбросить счётчик, и они не равнозначны:

```cpp
lastRun = millis();            // вариант А
lastRun += INTERVAL;           // вариант Б
```

**Вариант А** отсчитывает интервал от момента фактического срабатывания. Если `loop()` задержался на 3 мс, эти 3 мс добавятся к периоду, и ошибка будет накапливаться - за час набегут секунды.

**Вариант Б** привязывается к идеальной сетке: пропущенное время не накапливается, средний период точно равен `INTERVAL`. Именно так делают часы и любые задачи с фиксированной частотой.

Оборотная сторона варианта Б: если программа зависла надолго, условие сработает несколько раз подряд, "догоняя" расписание. Для мигания светодиодом это неважно, для управления - может быть нежелательно.

## 3. Несколько независимых задач

Каждой задаче - своя переменная времени и свой интервал:

```cpp
const int LED_FAST = 8, LED_SLOW = 9, BUTTON = 2;

unsigned long tFast = 0, tSlow = 0, tSensor = 0;
const unsigned long P_FAST = 100, P_SLOW = 1000, P_SENSOR = 2000;

bool fastState = false, slowState = false;

void setup() {
    pinMode(LED_FAST, OUTPUT);
    pinMode(LED_SLOW, OUTPUT);
    pinMode(BUTTON, INPUT_PULLUP);
    Serial.begin(9600);
}

void loop() {
    unsigned long now = millis();       // одно чтение на итерацию - быстрее и согласованнее

    if (now - tFast >= P_FAST) {
        tFast += P_FAST;
        fastState = !fastState;
        digitalWrite(LED_FAST, fastState);
    }

    if (now - tSlow >= P_SLOW) {
        tSlow += P_SLOW;
        slowState = !slowState;
        digitalWrite(LED_SLOW, slowState);
    }

    if (now - tSensor >= P_SENSOR) {
        tSensor += P_SENSOR;
        Serial.println(analogRead(A0));
    }

    // кнопка опрашивается на каждой итерации - реакция мгновенная
    if (digitalRead(BUTTON) == LOW) {
        // ...
    }
}
```

Два светодиода мигают с разной частотой, датчик опрашивается раз в две секунды, кнопка реагирует немедленно. На `delay()` такую программу написать невозможно.

Это и есть **кооперативная многозадачность**: задачи не вытесняют друг друга, а по очереди получают управление и **добровольно** его возвращают. Планировщика нет - его роль играет `loop()`.

### Главное правило кооперативной модели

**Ни одна задача не должна выполняться долго.** Отзывчивость системы определяется самой медленной операцией в цикле.

Если одна из задач вызовет `delay(1000)`, встанет вся программа. Поэтому в такой архитектуре запрещены:

- `delay()` длиннее нескольких миллисекунд;
- ожидание в цикле `while (!condition) {}`;
- длинные вычисления в одном проходе;
- блокирующие библиотечные вызовы (`dht.readTemperature()` держит процессор ~20 мс, `stepper.step(2048)` - секунды).

Максимальную длительность одной итерации полезно измерять:

```cpp
void loop() {
    unsigned long start = micros();
    // ... вся работа ...
    unsigned long elapsed = micros() - start;

    static unsigned long worst = 0;
    if (elapsed > worst) {
        worst = elapsed;
        Serial.print(F("Худшая итерация, мкс: "));
        Serial.println(worst);
    }
}
```

Эта величина - **время реакции** вашей системы на любое событие. Если оно составляет 20 мс, кнопку, нажатую на 15 мс, программа пропустит.

## 4. Конечные автоматы

Неблокирующий код быстро становится запутанным, если у задачи есть несколько последовательных стадий. Решение - **конечный автомат** (**F**inite **S**tate **M**achine, **FSM**): явный перечень состояний, переменная текущего состояния и правила переходов.

### Пример: светофор

Блокирующая версия, которую нельзя ни прервать, ни совместить с чем-то ещё:

```cpp
void loop() {
    digitalWrite(GREEN, HIGH);  delay(5000);  digitalWrite(GREEN, LOW);
    digitalWrite(YELLOW, HIGH); delay(2000);  digitalWrite(YELLOW, LOW);
    digitalWrite(RED, HIGH);    delay(5000);  digitalWrite(RED, LOW);
}
```

Версия на конечном автомате:

```cpp
enum State { GREEN_ON, YELLOW_ON, RED_ON };

State state = GREEN_ON;
unsigned long stateStart = 0;

void enterState(State s) {
    state = s;
    stateStart = millis();
    digitalWrite(GREEN,  s == GREEN_ON);
    digitalWrite(YELLOW, s == YELLOW_ON);
    digitalWrite(RED,    s == RED_ON);
}

void loop() {
    unsigned long elapsed = millis() - stateStart;

    switch (state) {
        case GREEN_ON:
            if (elapsed >= 5000) enterState(YELLOW_ON);
            break;
        case YELLOW_ON:
            if (elapsed >= 2000) enterState(RED_ON);
            break;
        case RED_ON:
            if (elapsed >= 5000) enterState(GREEN_ON);
            break;
    }

    // здесь можно опрашивать кнопки, датчики, Serial - светофор этому не мешает
}
```

Кода стало больше, но появились свойства, которых не было:

- программа в любой момент знает, **в каком состоянии находится**, - это можно вывести в Serial;
- в цикл можно добавить сколько угодно других задач;
- легко добавить внешнее воздействие: "по нажатию кнопки немедленно перейти в `YELLOW_ON`" - это одна строка;
- поведение можно нарисовать диаграммой и проверить логику до написания кода.

### Диаграмма состояний

Прежде чем писать код автомата, нарисуйте его:

```tikz Конечный автомат светофора: три состояния и условия переходов
\begin{tikzpicture}[x=1cm,y=1cm]
  \node[device] (green)  at (0,0)   {GREEN\_ON};
  \node[tool]   (yellow) at (5,0)   {YELLOW\_ON};
  \node[alert]  (red)    at (10,0)  {RED\_ON};

  \draw[flow] (green) -- node[lab, above, align=center] {нажата кнопка}
                         node[sublab, below] {ждём 5000 мс} (yellow);
  \draw[flow] (yellow) -- node[sublab, below] {ждём 2000 мс} (red);
  \draw[flow] (red.north) .. controls +(0,1.9) and +(0,1.9) ..
              node[lab, above] {через 5000 мс} (green.north);
  \node[note, anchor=north, align=center] at (5,-1.5)
       {пока кнопка не нажата, автомат остаётся в GREEN\_ON};
\end{tikzpicture}
```

Такая диаграмма - это уже половина отчёта по лабораторной работе, и она сразу выявляет пробелы: что произойдёт при нажатии кнопки в состоянии `RED_ON`? Что если кнопку нажать дважды?

### Вложенные автоматы

В реальной программе автоматов обычно несколько: автомат меню, автомат кнопки, автомат опроса датчика. Они работают параллельно в одном `loop()`, каждый со своей переменной состояния. Такая структура хорошо масштабируется и лежит в основе лабораторной работы **N3**.

## 5. Разделение программы на модули

Когда задач становится больше трёх, `loop()` превращается в кашу. Стандартный приём - каждой задаче своя функция вида `taskXxx()`, а `loop()` только вызывает их по очереди:

```cpp
void taskBlink();
void taskButton();
void taskSensor();
void taskDisplay();

void loop() {
    taskBlink();
    taskButton();
    taskSensor();
    taskDisplay();
}

void taskBlink() {
    static unsigned long ts = 0;        // состояние задачи живёт внутри неё
    static bool state = false;
    if (millis() - ts < 500) return;    // ранний выход - задача ещё "спит"
    ts += 500;
    state = !state;
    digitalWrite(LED, state);
}
```

Два приёма, которые стоит взять на вооружение:

- **`static` внутри функции**. Переменная сохраняет значение между вызовами, но не видна снаружи - это *локальная глобальная переменная*. Она уменьшает количество глобальных переменных и делает задачу самодостаточной.
- **Ранний выход `return`**. Вместо `if (пора) { ... }` с большим телом - проверка "ещё не пора -> выйти". Код становится плоским, без глубокой вложенности.

Такая структура - прямой предшественник настоящей ОСРВ. В [занятии 16](../19-freertos-tasks/note.md) каждая `taskXxx()` превратится в отдельную задачу FreeRTOS со своим стеком, и вместо ручного `return` появится `vTaskDelay()`.

## 6. Ограничения подхода

Кооперативная многозадачность проста, не требует дополнительной памяти и полностью предсказуема. Но у неё есть границы применимости:

| Проблема | Проявление |
| --- | --- |
| **Нет гарантии времени реакции** | Одна медленная задача задерживает все остальные |
| **Нет приоритетов** | Критичная задача ждёт в общей очереди наравне с выводом на дисплей |
| **Задачу нельзя "приостановить"** | Каждая задача обязана сама быстро вернуть управление |
| **Ручное управление состоянием** | Последовательный алгоритм приходится выворачивать в автомат |

Первые две проблемы решаются **прерываниями** ([занятие 8](../08-interrupts/note.md)): аппаратура прерывает выполнение основной программы и мгновенно передаёт управление обработчику.

Последние две решаются **операционной системой реального времени** ([занятия 16-18](../19-freertos-tasks/note.md)): планировщик сам переключает задачи, и линейный алгоритм с ожиданиями можно писать "как есть".
