# Занятие 20. FreeRTOS: синхронизация и обмен данными

**Цель занятия:** научиться безопасно передавать данные между задачами и защищать разделяемые ресурсы; разобраться в гонках данных, взаимных блокировках и приоритетной инверсии.

**Что понадобится:** Arduino UNO, PlatformIO, датчики, дисплей, кнопки, светодиоды.

---

## 1. Проблема разделяемых данных

Как только задач становится больше одной, возникает вопрос: как им обмениваться информацией?

Наивный ответ - через глобальную переменную:

```cpp
volatile int temperature = 0;

void TaskSensor(void *pv) {
    for (;;) {
        temperature = readSensor();
        vTaskDelay(pdMS_TO_TICKS(1000));
    }
}

void TaskDisplay(void *pv) {
    for (;;) {
        showValue(temperature);
        vTaskDelay(pdMS_TO_TICKS(200));
    }
}
```

Для одного `int` это может сработать. Но стоит усложнить задачу, и появляются ошибки, которые проявляются раз в час и не воспроизводятся при отладке.

### Гонка данных

Пусть задачи обмениваются структурой:

```cpp
struct Measurement {
    float temperature;
    float humidity;
    unsigned long timestamp;
};

Measurement shared;         // 12 байт
```

Задача-датчик записывает поля по очереди. Планировщик может вытеснить её **в любой момент** - например, после записи температуры, но до записи влажности. Задача-дисплей в это время прочитает **новую температуру со старой влажностью**.

Данные формально корректны, каждое поле осмысленно, но вместе они описывают момент, которого никогда не было. Найти такую ошибку по симптомам практически невозможно.

### Неатомарные операции

Даже одна переменная небезопасна, если она больше байта. На 8-разрядном AVR:

```cpp
volatile unsigned long counter;      // 4 байта

counter++;      // читать 4 байта, прибавить 1, записать 4 байта - до 12 инструкций
```

Переключение задач между этими инструкциями даёт потерянное или искажённое значение. Это та же проблема, что и с обработчиками прерываний ([занятие 8](../08-interrupts/note.md)), только источник вытеснения другой.

### Критическая секция

Участок кода, который должен выполниться целиком, называется **критической секцией**. FreeRTOS даёт для них примитивы:

```cpp
taskENTER_CRITICAL();
// несколько инструкций, которые нельзя прерывать
taskEXIT_CRITICAL();
```

Внутри запрещены прерывания и переключение задач. Отсюда правило: **критическая секция должна быть максимально короткой** - иначе страдает время реакции всей системы.

Для длительных операций критическая секция не годится. Для них есть мьютексы.

## 2. Мьютекс

**Мьютекс** (mutex, от mutual exclusion - взаимное исключение) - механизм, гарантирующий, что ресурсом в каждый момент пользуется только одна задача.

Аналогия: ключ от переговорной. Хочешь войти - возьми ключ. Ключ один, поэтому одновременно внутри окажется только один человек. Ушёл - верни ключ.

```cpp
SemaphoreHandle_t xSerialMutex;

void setup() {
    Serial.begin(9600);
    xSerialMutex = xSemaphoreCreateMutex();

    if (xSerialMutex == NULL) {
        // не хватило памяти
    }
}

void printSafe(const char *text) {
    if (xSemaphoreTake(xSerialMutex, portMAX_DELAY) == pdTRUE) {
        Serial.println(text);                 // ресурс занят только этой задачей
        xSemaphoreGive(xSerialMutex);
    }
}
```

`xSemaphoreTake()` с параметром `portMAX_DELAY` блокирует задачу до освобождения мьютекса. Можно указать таймаут:

```cpp
if (xSemaphoreTake(xSerialMutex, pdMS_TO_TICKS(100)) == pdTRUE) {
    // получили доступ
    xSemaphoreGive(xSerialMutex);
} else {
    // за 100 мс не дождались - ресурс занят
}
```

Вариант с таймаутом предпочтителен: он не даёт задаче зависнуть навсегда из-за ошибки в другом месте программы.

### Что защищать мьютексом

- **Разделяемое устройство**: Serial, дисплей, шина I2C или SPI, к которым обращаются несколько задач;
- **Разделяемую структуру данных**, которая обновляется не за одну операцию;
- **Любой ресурс, который не терпит одновременного использования**.

Наглядный пример без мьютекса - две задачи печатают в Serial:

```
Задача A: Serial.print("Temp: "); <- вытеснена
Задача B: Serial.println("Button pressed");
Задача A: Serial.println(25);

Результат: "Temp: Button pressed
            25"
```

### Правила работы с мьютексом

1. **Каждому `Take` - свой `Give`.** Забытый `Give` блокирует ресурс навсегда.
2. **Держите мьютекс минимальное время.** Взяли, сделали, отдали. Никаких `vTaskDelay()` внутри.
3. **Не берите мьютекс из обработчика прерывания.** Обработчик не может блокироваться; для ISR существуют отдельные функции с суффиксом `FromISR`.
4. **Соблюдайте одинаковый порядок захвата**, если мьютексов несколько (см. раздел про взаимную блокировку).

## 3. Взаимная блокировка и приоритетная инверсия

### Взаимная блокировка (deadlock)

Две задачи взяли по одному мьютексу и ждут второй:

```cpp
// Задача A
xSemaphoreTake(mutexI2C, portMAX_DELAY);
xSemaphoreTake(mutexDisplay, portMAX_DELAY);   // ждёт, пока B освободит

// Задача B
xSemaphoreTake(mutexDisplay, portMAX_DELAY);
xSemaphoreTake(mutexI2C, portMAX_DELAY);       // ждёт, пока A освободит
```

Обе задачи заблокированы навсегда. Система выглядит зависшей, хотя формально работает.

Способы избежать:

- **единый порядок захвата**: если все задачи берут мьютексы в одном и том же порядке, взаимная блокировка невозможна;
- **таймауты вместо `portMAX_DELAY`**: задача не зависнет, а сможет откатиться и попробовать снова;
- **не держать два мьютекса одновременно**, если это возможно.

### Приоритетная инверсия

Более тонкая проблема:

1. Низкоприоритетная задача L захватывает мьютекс.
2. Появляется высокоприоритетная задача H, которой нужен тот же мьютекс. Она блокируется.
3. Появляется среднеприоритетная задача M, не связанная с мьютексом. Она **вытесняет L**, потому что приоритет выше.
4. Пока M работает, L не выполняется и не может отдать мьютекс. Значит и H стоит.

Получается, что задача M блокирует задачу H, имея меньший приоритет. Именно эта ошибка привела к периодическим перезагрузкам марсохода Mars Pathfinder в 1997 году.

**Решение - наследование приоритета:** пока высокоприоритетная задача ждёт мьютекс, владелец мьютекса временно получает её приоритет и не может быть вытеснен задачей среднего приоритета.

Мьютексы FreeRTOS (`xSemaphoreCreateMutex`) **поддерживают наследование приоритета**. Двоичные семафоры (`xSemaphoreCreateBinary`) - **нет**. Отсюда правило: **для защиты ресурса используйте мьютекс, а не двоичный семафор**.

## 4. Семафоры

Семафор служит не для защиты ресурса, а для **сигнализации между задачами**.

### Двоичный семафор

Аналогия: флажок. Одна задача его поднимает (событие произошло), другая ждёт и опускает.

```cpp
SemaphoreHandle_t xButtonSemaphore;

void setup() {
    xButtonSemaphore = xSemaphoreCreateBinary();
    attachInterrupt(digitalPinToInterrupt(2), onButtonISR, FALLING);
    xTaskCreate(TaskHandleButton, "Btn", 128, NULL, 2, NULL);
}

void onButtonISR() {
    BaseType_t xHigherPriorityTaskWoken = pdFALSE;
    xSemaphoreGiveFromISR(xButtonSemaphore, &xHigherPriorityTaskWoken);
    if (xHigherPriorityTaskWoken) taskYIELD();
}

void TaskHandleButton(void *pv) {
    for (;;) {
        if (xSemaphoreTake(xButtonSemaphore, portMAX_DELAY) == pdTRUE) {
            // кнопка нажата: здесь можно делать сколь угодно долгую работу
            handleButtonPress();
        }
    }
}
```

Это каноническая схема "отложенной обработки прерывания": обработчик делает минимум (даёт семафор), а вся работа выполняется в обычной задаче, где доступны все возможности системы. Подробно - на [занятии 21](../21-freertos-isr/note.md).

Обратите внимание: задача не опрашивает кнопку в цикле. Она **заблокирована** и не тратит процессорное время, пока событие не произойдёт.

### Считающий семафор

Хранит счётчик - используется для учёта нескольких одинаковых ресурсов или подсчёта событий:

```cpp
SemaphoreHandle_t xCounting = xSemaphoreCreateCounting(10, 0);   // максимум 10, начальное 0
```

Каждый `Give` увеличивает счётчик, каждый `Take` уменьшает. Если счётчик нулевой, `Take` блокирует задачу.

### Мьютекс или семафор

| | Мьютекс | Двоичный семафор |
| --- | --- | --- |
| Назначение | Защита ресурса | Сигнализация о событии |
| Владелец | Есть: отдать может только тот, кто взял | Нет: дать может кто угодно |
| Наследование приоритета | Есть | Нет |
| Использование из ISR | Нельзя | Можно (`GiveFromISR`) |
| Начальное состояние | Свободен | Пуст |

## 5. Очереди

**Очередь** - основной механизм передачи данных между задачами в FreeRTOS. Она решает сразу три проблемы: передачу данных, синхронизацию и буферизацию.

```cpp
QueueHandle_t xSensorQueue;

struct Measurement {
    float temperature;
    float humidity;
};

void setup() {
    xSensorQueue = xQueueCreate(5, sizeof(Measurement));   // 5 элементов

    if (xSensorQueue == NULL) {
        Serial.println(F("Не хватило памяти на очередь"));
    }

    xTaskCreate(TaskSensor,  "Sens", 192, NULL, 2, NULL);
    xTaskCreate(TaskDisplay, "Disp", 192, NULL, 1, NULL);
}

void TaskSensor(void *pv) {
    for (;;) {
        Measurement m;
        m.temperature = readTemperature();
        m.humidity = readHumidity();

        xQueueSend(xSensorQueue, &m, pdMS_TO_TICKS(10));   // копия помещается в очередь
        vTaskDelay(pdMS_TO_TICKS(2000));
    }
}

void TaskDisplay(void *pv) {
    Measurement m;
    for (;;) {
        if (xQueueReceive(xSensorQueue, &m, portMAX_DELAY) == pdTRUE) {
            showOnDisplay(m.temperature, m.humidity);
        }
    }
}
```

### Почему очередь лучше глобальной переменной

**Передаётся копия.** `xQueueSend()` копирует данные внутрь очереди. Отправитель может немедленно изменить свою переменную - на уже отправленные данные это не повлияет. Гонки данных исключены по построению.

**Встроенная синхронизация.** Библиотека сама защищает внутренние структуры. Мьютекс не нужен.

**Буферизация.** Если получатель занят, данные накапливаются в очереди и не теряются - до заполнения.

**Блокировка вместо опроса.** `xQueueReceive()` с `portMAX_DELAY` блокирует задачу до появления данных. Задача не тратит процессорное время впустую.

### Управление таймаутами

```cpp
xQueueSend(queue, &item, 0);                    // не ждать: если полна - сразу ошибка
xQueueSend(queue, &item, pdMS_TO_TICKS(100));   // ждать до 100 мс
xQueueSend(queue, &item, portMAX_DELAY);        // ждать бесконечно
```

Выбор таймаута отправки - проектное решение:

- **`portMAX_DELAY`** - данные важнее скорости, задача подождёт;
- **`0`** - скорость важнее, лучше потерять отсчёт, чем задержать задачу;
- **конечный таймаут** - компромисс с обработкой отказа.

Всегда проверяйте результат:

```cpp
if (xQueueSend(xSensorQueue, &m, 0) != pdTRUE) {
    droppedCount++;                             // очередь переполнена, считаем потери
}
```

### Полезные функции

```cpp
uxQueueMessagesWaiting(queue);      // сколько элементов сейчас в очереди
uxQueueSpacesAvailable(queue);      // сколько свободных мест
xQueuePeek(queue, &item, timeout);  // посмотреть, не извлекая
xQueueReset(queue);                 // очистить
xQueueSendToFront(queue, &item, t); // отправить в начало (срочное сообщение)
```

### Размер очереди

Очередь занимает `количество * размер_элемента` байт плюс служебные данные. На UNO это существенно:

```
Очередь на 5 элементов по 8 байт = 40 байт данных + ~30 байт служебных = 70 байт
```

При 2 КБ ОЗУ больше 2-3 небольших очередей позволить себе трудно.

Правило выбора длины: очередь должна сглаживать **кратковременную** разницу в скорости отправителя и получателя. Если получатель систематически медленнее, никакая длина не спасёт - очередь всё равно переполнится.

## 6. Архитектурные шаблоны

### Производитель - потребитель

Базовый шаблон: одна задача порождает данные, другая обрабатывает.

```
  TaskSensor  --[очередь]-->  TaskProcess  --[очередь]-->  TaskDisplay
  (2 с)                        (по мере                    (по мере
                               поступления)                 поступления)
```

Каждая задача блокируется на своей очереди и просыпается только при появлении работы. Процессорное время не тратится на опрос.

### Централизованный доступ к ресурсу

Вместо того чтобы защищать дисплей мьютексом, ему выделяют **отдельную задачу** с очередью команд:

```cpp
struct DisplayCommand {
    uint8_t row;
    char text[16];
};

QueueHandle_t xDisplayQueue;

void TaskDisplay(void *pv) {
    DisplayCommand cmd;
    lcd.begin(16, 2);
    for (;;) {
        if (xQueueReceive(xDisplayQueue, &cmd, portMAX_DELAY) == pdTRUE) {
            lcd.setCursor(0, cmd.row);
            lcd.print(cmd.text);
        }
    }
}
```

Теперь **только эта задача** обращается к дисплею. Мьютекс не нужен, гонок нет, а остальные задачи просто отправляют команды и не ждут.

Шаблон особенно хорош для медленных устройств: отправитель не блокируется на время вывода.

### Разделение по времени реакции

```cpp
xTaskCreate(TaskSafety,  "Safe", 128, NULL, 3, NULL);   // реакция < 50 мс
xTaskCreate(TaskControl, "Ctrl", 192, NULL, 2, NULL);   // реакция < 200 мс
xTaskCreate(TaskLog,     "Log",  192, NULL, 1, NULL);   // когда есть время
```

Приоритет назначается не по "важности" в бытовом смысле, а по **допустимому времени реакции**.

## 7. Отладка многозадачных программ

Ошибки синхронизации плавающие и плохо воспроизводимые. Полезные приёмы:

**Считайте всё.** Отправленные и принятые сообщения, потерянные из-за переполнения, неудачные захваты мьютекса. Расхождение счётчиков сразу укажет на проблему.

```cpp
volatile uint16_t sent = 0, received = 0, dropped = 0;
```

**Следите за заполнением очередей.** Растущее число элементов означает, что получатель не успевает.

**Проверяйте остаток стека каждой задачи** через `uxTaskGetStackHighWaterMark()`.

**Задача-монитор.** Низкоприоритетная задача, раз в несколько секунд печатающая состояние системы: счётчики, свободную кучу, остатки стеков.

```cpp
void TaskMonitor(void *pv) {
    for (;;) {
        Serial.print(F("heap="));    Serial.print(xPortGetFreeHeapSize());
        Serial.print(F(" queue="));  Serial.print(uxQueueMessagesWaiting(xSensorQueue));
        Serial.print(F(" sent="));   Serial.print(sent);
        Serial.print(F(" drop="));   Serial.println(dropped);
        vTaskDelay(pdMS_TO_TICKS(5000));
    }
}
```

**Не отлаживайте печатью изнутри критических секций.** Вывод в Serial сам по себе долгий и может изменить тайминги настолько, что ошибка исчезнет - и появится снова, как только отладочную печать уберут.
