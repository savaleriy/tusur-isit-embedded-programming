# Занятие 19. FreeRTOS: задачи и планировщик

**Цель занятия:** понять, что даёт операционная система реального времени, запустить первые задачи на Arduino UNO и научиться считать память, которой на этой плате крайне мало.

**Что понадобится:** Arduino UNO, PlatformIO, светодиоды, кнопки, любой датчик.

---

## 1. Куда упирается кооперативная многозадачность

На [занятии 7](../07-timing-multitasking/note.md) мы научились делать несколько дел одновременно: каждая задача получает управление, быстро делает свою работу и возвращает его.

Схема работает, пока соблюдается **главное условие: ни одна задача не выполняется долго**. Как только это условие нарушается, система разваливается:

```cpp
void loop() {
    taskBlink();        // 10 мкс
    taskButton();       // 20 мкс
    taskSensor();       // 20 мс - чтение DHT-11 блокирует всё
    taskDisplay();      // 15 мс - обновление TFT
}
```

Время реакции такой системы - 35 мс. Кнопку, нажатую на 30 мс, программа пропустит.

Проблемы, которые нельзя решить в кооперативной модели:

| Проблема | Суть |
| --- | --- |
| **Нет приоритетов** | Критичная задача ждёт в общей очереди наравне с обновлением дисплея |
| **Нет вытеснения** | Медленная задача блокирует все остальные и её нельзя прервать |
| **Линейный алгоритм приходится выворачивать** | Любое ожидание превращается в конечный автомат |
| **Нет гарантий времени** | Время реакции зависит от суммы всех задач |

Особенно неприятен третий пункт. Простой линейный алгоритм:

```
включить нагреватель
подождать 5 секунд
измерить температуру
если больше порога - выключить и подождать 10 секунд
повторить
```

В кооперативной модели это превращается в автомат на 4 состояния с переменными времени. В ОСРВ он пишется буквально так, как записан выше.

## 2. Что такое ОСРВ

**Операционная система реального времени** (ОСРВ, RTOS) - это, прежде всего, **планировщик**: код, который сам решает, какая задача выполняется в данный момент, и переключает их.

Ключевое отличие от кооперативной модели - **вытеснение** (preemption). Планировщик может остановить задачу **в любой точке**, сохранить её состояние и передать управление другой. Задача даже не узнает, что её прерывали.

### Что нужно, чтобы это работало

**У каждой задачи свой стек.** Задача может быть остановлена посреди вызова функции, значит её локальные переменные и адреса возврата должны где-то жить. Это главная плата за ОСРВ на плате с 2 КБ ОЗУ.

**Переключение контекста.** При смене задачи планировщик сохраняет все 32 регистра, `SREG` и указатель стека текущей задачи, затем восстанавливает то же самое для новой. На AVR это занимает порядка 100 тактов.

**Системный тик.** Периодическое прерывание, по которому планировщик пересматривает решение: не пора ли переключить задачу.

### Состояния задачи

```tikz Состояния задачи FreeRTOS и переходы между ними

  \node[device] (ready)   at (0,0)     {READY};
  \node[mcu]    (running) at (6.4,0)   {RUNNING};
  \node[tool]   (blocked) at (6.4,-3.4){BLOCKED};
  \node[host]   (susp)    at (0,-3.4)  {SUSPENDED};

  \draw[flow] ([yshift=3.5mm] ready.east) -- node[lab, above] {планировщик выбрал}
              ([yshift=3.5mm] running.west);
  \draw[flow] ([yshift=-3.5mm] running.west) -- node[lab, below, align=center]
              {квант истёк или появилась\\более приоритетная задача}
              ([yshift=-3.5mm] ready.east);
  \draw[flow] (running) -- node[lab, right, align=left]
              {\ttfamily vTaskDelay()\\ожидание очереди\\или семафора} (blocked);
  \draw[flow] (blocked.west) -- node[lab, below, align=center]
              {время вышло или\\ресурс освободился} (susp.east);
  \draw[flow] (susp.north) -- node[lab, left, align=right]
              {\ttfamily vTaskResume()} (ready.south);
  \draw[flow] ([xshift=-4mm] ready.south) ++(0,0)
              .. controls +(-2.2,-1.2) and +(-2.2,1.2) ..
              node[lab, left, align=right] {\ttfamily vTaskSuspend()}
              ([xshift=-4mm] susp.north);
  \draw[flow, draw=ok] (-3.6,1.9) -- node[lab, above, pos=0.3] {создание задачи}
              (ready.north west);

  \node[note, anchor=north, align=center] at (3.2,-4.9)
    {в состоянии BLOCKED задача не тратит процессорное время -\\

\end{tikzpicture}
```

| Состояние | Что означает |
| --- | --- |
| **Running** | Выполняется сейчас. На одноядерном МК такая задача ровно одна |
| **Ready** | Готова выполняться, ждёт своей очереди |
| **Blocked** | Ждёт события: истечения времени, данных в очереди, семафора. **Процессорное время не тратит** |
| **Suspended** | Приостановлена явным вызовом, не будет выполняться до `vTaskResume()` |

Состояние **Blocked** - главная ценность ОСРВ. Задача, ожидающая данные, не крутит пустой цикл, а просто исключается из рассмотрения планировщиком. Процессор в это время занят другими задачами или спит.

### Планирование по приоритетам

FreeRTOS использует **вытесняющее планирование с приоритетами**:

1. Всегда выполняется задача с **наивысшим приоритетом** из готовых.
2. Если готовых задач с одинаковым приоритетом несколько, они делят время поровну (round-robin).
3. Как только более приоритетная задача становится готовой, текущая **немедленно вытесняется**.

Отсюда важное следствие: **высокоприоритетная задача, которая никогда не блокируется, полностью займёт процессор**. Все задачи с меньшим приоритетом просто не будут выполняться. Это самая частая ошибка новичков в ОСРВ.

## 3. FreeRTOS на Arduino UNO

FreeRTOS - самая распространённая ОСРВ для микроконтроллеров: открытый исходный код, лицензия MIT, поддержка практически всех архитектур.

Для AVR используется порт [**Arduino_FreeRTOS_Library** (автор feilipu)](https://github.com/feilipu/Arduino_FreeRTOS_Library).

```ini
[env:uno]
platform = atmelavr
board = uno
framework = arduino
lib_deps = feilipu/FreeRTOS@^11.1.0-3
```

### Честный разговор о ресурсах

Arduino UNO - **не самая подходящая платформа** для ОСРВ, и об этом нужно сказать прямо.

| Ресурс | Сколько есть | Сколько нужно FreeRTOS |
| --- | --- | --- |
| SRAM | 2048 байт | ~200 байт на ядро планировщика |
| Стек одной задачи | - | минимум 85-100 байт, реально 128-200 |
| Flash | 32 КБ | 6-10 КБ на ядро |

Практический предел - **3-5 задач**. Стек каждой задачи выделяется из тех же 2 КБ, и переполнение стека проявляется как случайные необъяснимые сбои.

Зачем тогда изучать ОСРВ на UNO? Затем, что **концепции переносятся полностью**. Задачи, приоритеты, очереди, семафоры, приоритетная инверсия работают одинаково на UNO, на STM32 и на промышленном контроллере. Именно ограниченность UNO заставляет считать байты и понимать, что происходит, - на плате с 512 КБ ОЗУ этому не научишься.

### Источник системного тика

Порт FreeRTOS для AVR по умолчанию использует **сторожевой таймер (WDT)** в качестве источника тика, а не обычный таймер. Это сделано специально, чтобы не отбирать у пользователя Timer0, Timer1 и Timer2.

Практические следствия:

- `millis()`, `delay()`, ШИМ, `Servo` и `tone()` продолжают работать;
- разрешение системного тика - **15 мс** (значение по умолчанию `portUSE_WDTO = WDTO_15MS`);
- `vTaskDelay(pdMS_TO_TICKS(20))` фактически даст 15 или 30 мс, а не 20.

Грубость тика - характерная особенность именно этого порта. Её нужно учитывать: FreeRTOS на UNO не даёт миллисекундной точности, и всё, что требует точных интервалов, по-прежнему делается таймерами и прерываниями.

## 4. Первая программа

```cpp
#include <Arduino.h>
#include <Arduino_FreeRTOS.h>

void TaskBlinkFast(void *pvParameters);
void TaskBlinkSlow(void *pvParameters);
void TaskSerial(void *pvParameters);

void setup() {
    Serial.begin(9600);

    xTaskCreate(TaskBlinkFast, "Fast",  128, NULL, 1, NULL);
    xTaskCreate(TaskBlinkSlow, "Slow",  128, NULL, 1, NULL);
    xTaskCreate(TaskSerial,    "Ser",   192, NULL, 1, NULL);

    // vTaskStartScheduler() вызывается библиотекой автоматически после setup()
}

void loop() {
    // выполняется как задача Idle, обычно остаётся пустым
}

void TaskBlinkFast(void *pvParameters) {
    (void) pvParameters;
    pinMode(8, OUTPUT);

    for (;;) {                                  // задача никогда не завершается
        digitalWrite(8, HIGH);
        vTaskDelay(pdMS_TO_TICKS(100));
        digitalWrite(8, LOW);
        vTaskDelay(pdMS_TO_TICKS(100));
    }
}

void TaskBlinkSlow(void *pvParameters) {
    (void) pvParameters;
    pinMode(9, OUTPUT);

    for (;;) {
        digitalWrite(9, !digitalRead(9));
        vTaskDelay(pdMS_TO_TICKS(750));
    }
}

void TaskSerial(void *pvParameters) {
    (void) pvParameters;

    for (;;) {
        Serial.print(F("uptime, ticks: "));
        Serial.println(xTaskGetTickCount());
        vTaskDelay(pdMS_TO_TICKS(1000));
    }
}
```

Обратите внимание, насколько это похоже на обычный последовательный код. Никаких `millis()`, никаких переменных времени, никаких конечных автоматов - каждая задача написана так, будто она в программе одна.

### Разбор xTaskCreate

```cpp
xTaskCreate(
    TaskBlinkFast,   // функция задачи
    "Fast",          // имя (для отладки)
    128,             // размер стека
    NULL,            // параметр, передаваемый в задачу
    1,               // приоритет
    NULL             // указатель на хендл задачи (если нужен)
);
```

**Размер стека.** В порте для AVR тип элемента стека однобайтный, поэтому число задаёт размер **в байтах**. Значение 128 - разумная отправная точка для простой задачи; задаче с `Serial.print` и локальными буферами нужно 192-256.

**Приоритет.** 0 - самый низкий (его имеет задача Idle). Чем больше число, тем выше приоритет.

**Параметр.** Позволяет использовать одну функцию для нескольких задач:

```cpp
struct LedConfig { uint8_t pin; uint16_t periodMs; };

static LedConfig led1 = { 8, 100 };
static LedConfig led2 = { 9, 750 };

xTaskCreate(TaskBlink, "L1", 128, &led1, 1, NULL);
xTaskCreate(TaskBlink, "L2", 128, &led2, 1, NULL);

void TaskBlink(void *pvParameters) {
    LedConfig *cfg = (LedConfig *)pvParameters;
    pinMode(cfg->pin, OUTPUT);
    for (;;) {
        digitalWrite(cfg->pin, !digitalRead(cfg->pin));
        vTaskDelay(pdMS_TO_TICKS(cfg->periodMs));
    }
}
```

Структуры должны быть **глобальными или статическими**: локальная переменная `setup()` исчезнет к моменту запуска задачи.

### Задача не должна завершаться

Функция задачи - это бесконечный цикл. Если она вернёт управление, FreeRTOS вызовет обработчик ошибки и система остановится.

Если задача действительно должна завершиться, её удаляют явно:

```cpp
void TaskInit(void *pvParameters) {
    doInitialization();
    vTaskDelete(NULL);          // удалить саму себя
}
```

## 5. vTaskDelay и vTaskDelayUntil

### vTaskDelay

```cpp
vTaskDelay(pdMS_TO_TICKS(100));
```

Переводит задачу в состояние **Blocked** на указанное время. Это принципиально отличается от `delay()`:

| | `delay()` | `vTaskDelay()` |
| --- | --- | --- |
| Что делает процессор | Крутит пустой цикл | Выполняет другие задачи |
| Другие задачи | Стоят | Работают |
| Точность | ~1 мс | Кратна тику (15 мс на UNO) |

Макрос `pdMS_TO_TICKS()` переводит миллисекунды в тики. Писать `vTaskDelay(100)` неправильно: это 100 **тиков**, то есть полторы секунды при тике 15 мс.

### vTaskDelayUntil

`vTaskDelay()` отсчитывает время **от момента вызова**, поэтому период получается равным "задержка плюс время работы задачи" и слегка плавает.

Для строго периодических задач применяют `xTaskDelayUntil()`:

```cpp
void TaskSample(void *pvParameters) {
    TickType_t lastWake = xTaskGetTickCount();

    for (;;) {
        readSensor();                                        // время выполнения не важно
        xTaskDelayUntil(&lastWake, pdMS_TO_TICKS(100));      // ровно каждые 100 мс
    }
}
```

Это прямой аналог различия между `ts = millis()` и `ts += INTERVAL` с [занятия 7](../07-timing-multitasking/note.md), только реализованный операционной системой.

## 6. Приоритеты на практике

```cpp
xTaskCreate(TaskSafety,  "Safe", 128, NULL, 3, NULL);   // высокий: аварийный контроль
xTaskCreate(TaskControl, "Ctrl", 192, NULL, 2, NULL);   // средний: логика
xTaskCreate(TaskDisplay, "Disp", 256, NULL, 1, NULL);   // низкий: индикация
```

Правило распределения: **чем жёстче требование ко времени реакции, тем выше приоритет**.

- аварийные и защитные функции - наивысший;
- обработка ввода и управление - средний;
- индикация, логирование, связь - низкий.

### Классическая ошибка: задача, которая не блокируется

```cpp
void TaskBad(void *pvParameters) {
    for (;;) {
        if (digitalRead(BUTTON) == LOW) {
            doSomething();
        }
        // нет vTaskDelay - задача НИКОГДА не отдаёт управление добровольно
    }
}
```

Если у этой задачи высокий приоритет, все задачи с меньшим приоритетом **никогда не выполнятся**. Система выглядит зависшей, хотя формально работает.

Правило: **в каждом цикле задачи должна быть точка блокировки** - `vTaskDelay()`, ожидание очереди или семафора.

Если задача действительно должна опрашивать что-то непрерывно, ей нужен низкий приоритет и хотя бы `taskYIELD()`, добровольно уступающий управление равноприоритетным задачам.

## 7. Память: как не переполнить стек

Самая частая и самая неприятная проблема FreeRTOS на UNO.

### Что попадает в стек задачи

- локальные переменные всех вызванных функций;
- адреса возврата;
- сохранённый контекст (32 регистра плюс `SREG`) при вытеснении;
- контекст прерывания, если оно произошло во время выполнения задачи.

Отсюда минимум в 85-100 байт даже для пустой задачи.

### Признаки переполнения

Программа ведёт себя случайным образом: искажаются переменные **другой** задачи, происходят перезагрузки, зависания на ровном месте. Сообщений об ошибке нет - стек одной задачи просто залезает в чужую память.

### Измерение остатка стека

```cpp
void TaskMonitor(void *pvParameters) {
    for (;;) {
        Serial.print(F("Stack left: "));
        Serial.println(uxTaskGetStackHighWaterMark(NULL));
        vTaskDelay(pdMS_TO_TICKS(2000));
    }
}
```

Функция возвращает **минимальное** количество свободных байт стека за всё время работы задачи. Если передать `NULL` - для текущей задачи, можно передать и хендл другой.

Практика: запустите программу, дайте ей поработать во всех режимах, посмотрите значение. Оставляйте запас **не менее 30-50 байт**.

### Контроль переполнения

В `FreeRTOSConfig.h` можно включить проверку:

```c
#define configCHECK_FOR_STACK_OVERFLOW 2
```

Тогда при переполнении будет вызвана функция, которую вы реализуете:

```cpp
extern "C" void vApplicationStackOverflowHook(TaskHandle_t xTask, char *pcTaskName) {
    (void) xTask;
    Serial.print(F("STACK OVERFLOW in "));
    Serial.println(pcTaskName);
    Serial.flush();
    for (;;) { }                     // остановиться, чтобы не портить память дальше
}
```

Проверка стоит процессорного времени, поэтому её включают на время отладки.

### Свободная память кучи

FreeRTOS выделяет стеки задач из собственной кучи:

```cpp
Serial.print(F("Free heap: "));
Serial.println(xPortGetFreeHeapSize());
```

Размер кучи задаётся в `FreeRTOSConfig.h` параметром `configTOTAL_HEAP_SIZE`. На UNO приходится подбирать его вручную: слишком маленький - задачи не создадутся, слишком большой - не останется памяти на глобальные переменные.

### Проверка, что задача создалась

```cpp
if (xTaskCreate(TaskSensor, "Sens", 200, NULL, 2, NULL) != pdPASS) {
    Serial.println(F("Не удалось создать задачу: нет памяти"));
    Serial.flush();
    for (;;) { }
}
```

Без этой проверки нехватка памяти проявится как "одна из задач молча не работает" - и вы будете искать ошибку в её коде.

## 8. Задача Idle и функция loop

Планировщику всегда нужна хотя бы одна готовая задача. Когда все остальные заблокированы, выполняется задача **Idle** с приоритетом 0.

В порте для Arduino функция `loop()` выполняется именно как задача Idle. Отсюда:

- код в `loop()` работает **только когда все остальные задачи заблокированы**;
- писать туда что-то важное нельзя;
- обычно `loop()` оставляют пустым.

Задача Idle используется для полезного дела - перевода процессора в режим сна:

```cpp
extern "C" void vApplicationIdleHook(void) {
    set_sleep_mode(SLEEP_MODE_IDLE);
    sleep_mode();                     // проснётся по следующему прерыванию
}
```

Это заметно снижает потребление, ничего не ломая: при появлении готовой задачи процессор немедленно проснётся.

## 9. Когда ОСРВ не нужна

ОСРВ - инструмент, а не признак качества. На Arduino UNO она **чаще не нужна, чем нужна**.

**Не нужна, если:**

- задач меньше трёх и все они быстрые;
- кооперативная модель с `millis()` справляется;
- памяти в обрез (а на UNO она в обрез почти всегда);
- требуется жёсткая предсказуемость времени - здесь надёжнее прерывания.

**Нужна, если:**

- есть задачи с существенно разными требованиями ко времени реакции;
- есть долгие блокирующие операции, которые нельзя переписать;
- программа большая, и разделение на независимые задачи упрощает разработку;
- проект будет переноситься на более мощную платформу.

Честная оценка: типовой проект этого курса прекрасно решается кооперативной моделью. FreeRTOS изучается потому, что это стандартный инструмент отрасли и без него не понять следующий уровень - синхронизацию и обмен данными между задачами.
